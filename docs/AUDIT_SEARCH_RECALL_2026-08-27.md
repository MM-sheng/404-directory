## 2. 修复的问题

### 2.1 整句匹配漏掉相关工具

原逻辑要求完整查询连续出现。因此 `Official OpenAI developer documentation` 并不包含连续的 `official documentation`，即使明显相关也会返回零。

先添加的两条复现测试均失败，修复后通过，没有靠改测试查询掩盖问题。

### 2.2 两个存储后端的搜索字段不同

内存把能力标签加入文本搜索，PostgreSQL 原来只搜名称和说明。现在两者共用 `src/domain/catalog-search.ts`，在名称、slug、说明、能力、类别和提供方名称/slug 中查找关键词。

### 2.3 排序前截断漏掉最佳候选

PostgreSQL 原来在排序和信用过滤前只读 `min(limit * 3, 100)` 个 ID，既没有保证这些是最相关的，也可能在前几个都不达标时错报零结果。

现在先读取受状态、协议、类别约束的候选公开检索字段与排序统计，用统一逻辑筛选排序，再加载最终候选的完整详情。测试将最佳候选放在 106 条同类记录的最后，精确匹配与信用阈值查询都能得到它。

### 2.4 零结果缺少下一步，也可能增加激活数

MCP 与 REST 现在共用返回结构，保留 `count`、`tools`，增加：

- `search.algorithm_version: catalog-lexical-v2`；
- `search.result_status: matches | no_matches`；
- 当前保留的过滤条件；
- 零结果时的 `recovery`，指向 MCP `list_capabilities` / REST `/v1/capabilities`，建议人工缩短关键词或选择已有能力标签。

没有自动降低信用门槛、修改协议/类别或释放隔离记录来凑结果。合法空搜索仍返回普通 MCP 结果，不是协议异常；但计量为 `success=false / error_type=no_matches / result_count=0`，不再激活一个成功身份。现有 `failed_tool` 漏斗因此包含这种未找到候选的业务结果，不能把该项都理解成服务故障。

## 3. 明确的搜索契约

这是可解释的关键词检索，不是通用语义搜索或安全认证：

1. 大小写和 Unicode 兼容形式统一；空格、下划线、连字符和标点用于分词。
2. `doc` / `docs` / `documentation` 归一为 documentation。
3. 去除少量英文请求用语，例如 find、please、for；只有这些词时不自动变成全目录查询。
4. 所有有效词都必须匹配，可以位于不同字段。至少三个字符的查询词支持词首匹配，不是任意子串匹配。
5. 精确名称/slug 优先，其后按字段相关性、现有信用分（保留 degraded 惩罚）、七日调用量和稳定 slug 顺序排名。
6. capability 是规范化后的字面子串；`%`、`_` 不是数据库通配符。category 仍是精确匹配。
7. 公共查询只展示 active/degraded；隔离状态查询仍需要管理员。所有硬过滤先满足，排序不能绕过它们。
8. 空白 q 等价于带过滤的浏览；纯标点不会变成全目录通配查询。

用户指定的信用阈值仍使用已有信用分，但这个数不是经校准的安全概率。找到候选后仍须对精确 slug 调用 `evaluate_tool_risk`；搜索不执行第三方工具。
