# 404.directory 短期执行总规划

> 执行周期：2026-08-23 至 2026-12-31
> 文档状态：执行基线 v1
> 当前产品阶段：完成现有小工具、验证真实 Agent 使用、建立可信数据起点
> 年度目标：1,000 个去重后的真实外部 AI Agent，且每个 Agent 至少成功执行一次工具调用

## 0. 执行结论

404.directory 现在不是一个完整的 Agent 信用平台，也不应立刻扩张成保险、支付、通用身份或“万事万物可信度”平台。

它现在是一个面向 AI Agent 的工具发现、验证、比较和只读调用入口：Agent 可以通过 MCP 或 API 找工具、检查工具和服务商、搜索官方文档，并安全调用已登记的只读工具。

短期唯一正确路径是：

1. 把现有工具做到任何外部 Agent 都能安装并成功调用。
2. 获得首批真实外部 Agent，而不是继续累计匿名请求和页面浏览。
3. 为每次真实调用留下隐私安全、可去重、可归因的使用证据。
4. 用这些证据形成工具、服务商和兼容性的历史记录。
5. 到真实使用达到决策门槛后，再决定是否进入签名回执、Agent 身份和风险判断层。

短期护城河不是页面、工具数量或目录收录数量，而是逐渐积累的真实运行证据：哪个 Agent 客户端在什么版本下成功使用了哪个工具、工具是否稳定、服务商是否持续可用、失败发生在哪里、用户是否再次使用。

## 1. 不可更改的北极星指标

### 1.1 年度目标

到 2026-12-31，达到：

```text
identified_external_agents >= 1000
```

一个 Agent 只有同时满足以下条件才计入：

- 来自项目控制范围以外的真实外部用户或组织。
- 提供稳定的 Agent 标识；服务端只保存不可逆 HMAC，不保存原始标识。
- 至少完成一次真实工具调用，且结果为成功。
- 同一 Agent 的重复安装、重复会话和重复调用只计一次。
- 不是健康检查、爬虫、探针、项目自测、发布冒烟测试或维护者伪造流量。

以下数字不能作为年度目标成果：

- 网站访问量。
- Connect 页面浏览量。
- 安装按钮点击量。
- MCP `initialize` 或 `tools/list` 次数。
- 匿名成功调用。
- 内部测试调用。
- GitHub Star、目录收录数或提交中的 PR 数。

这些指标只能用来诊断漏斗，不能替代真实 Agent。

## 3. 产品边界

### 3.1 现在必须完成的产品

404.directory 的短期产品定义：

> 让任意 AI Agent 通过标准 MCP 接入一个可发现、可验证、可比较、可安全调用的工具入口，并为真实调用生成隐私安全的运行证据。

必须做到：

- 安装简单：远程 MCP 和 npm stdio 两条路径都能工作。
- 协议正确：主流 MCP 客户端可以初始化、列出工具并调用工具。
- 首次成功清晰：新用户在 5 分钟内完成真实调用。
- 结果真实：至少一个发现工具、一个验证工具、一个网关工具可在生产环境成功。
- 数据可信：可区分外部用户、自测、匿名请求和重复 Agent。
- 运行稳定：可以看到工具、服务商、来源和客户端的成功率与延迟。

### 3.2 现在明确不做

- 不做通用 Agent 社交身份。
- 不做单一的“万能信用分”。
- 不做保险、贷款、托管、支付或代币。
- 不做开放式写操作和高风险交易。
- 不为了目录规模加入大量未经验证的工具。
- 不拆成大量微服务。
- 不引入区块链、向量数据库或复杂事件平台，除非已有数据证明需要。
- 不保存原始 Agent ID、IP、提示词、工具参数、工具结果、密钥或隐私内容。

任何新功能只有满足以下至少一个条件才能进入开发：

1. 消除安装或首次调用中的已知失败。
2. 提高合格外部 Agent 的激活或留存。
3. 产生更可靠的工具、服务商或兼容性证据。

否则不做。

### 阶段 2：把“能安装”变成“5 分钟内成功”

- 一条首选安装方式。

- 一个真实首个任务。
- 一个成功结果示例。
- 一个失败排查入口。

首个任务不能只是 `tools/list`，必须调用真实工具。例如：


#### 步骤 2.2：让安装默认产生稳定身份

- npm bridge 为本机生成稳定随机 Agent ID。
- 服务端只保存不可逆 HMAC。
- 来源标签由安装入口传递，例如 `cursor-marketplace`、`official-registry`、`npm`。
- 用户可以重置本地 ID，但重置后视为新身份并标记异常增长风险。
- 远程 MCP 的纯匿名接入仍可使用，但不计入 1,000。

当前阶段的身份只是“稳定的隐私安全安装身份”，不是密码学 Agent Identity，也不能被宣传为信用身份。

### 阶段 3：获得首批 10 个真实外部 Agent

时间：发布后第 3 至 7 天。

#### 步骤 3.1：定义首批用户，不等待自然流量

优先邀请：

- 正在使用 Cursor、Claude、Codex 或其他 MCP 客户端的独立开发者。
- 正在开发 Agent，需要官方文档检索或工具发现能力的团队。
- 已经维护 MCP Server、希望检查兼容性和可见性的工具作者。
- 外部分发目录的维护者或审核者，但只有真实调用后才计数。

#### 步骤 3.2：给每位试点用户一个真实任务

每位用户完成以下流程：

1. 从指定来源安装。
2. 确认客户端看到 12 个工具。
3. 用自己的 Agent 完成一个与其工作相关的任务。
4. 至少成功调用一次工具。
5. 允许匿名 HMAC 计数和来源归因。
6. 反馈安装是否成功、首次成功耗时和失败阶段，不要求提供提示词或结果内容。

#### 步骤 3.3：逐个验证是否合格

每新增一个 Agent，检查：

- 外部分类为真。
- Agent HMAC 从未出现过。
- 至少一条成功调用。
- 不是内部、自测、探针或发布审核脚本。
- 来源和客户端不为空。

只有满足以上条件才更新 `identified_external_agents`。

#### 步骤 3.4：在第 10 个 Agent 后做第一次复盘

必须回答：

- 10 人中几人安装成功？
- 成功者从安装到首次调用用了多久？
- 失败最多发生在哪一步？
- 哪个工具最先被调用？
- 哪个渠道带来的 Agent 最多？
- 7 天后有几人再次使用？

只修复出现频率最高、直接影响首次成功的 1 至 2 个问题。不要根据单个意见扩张产品。

#### 步骤 4.3：每 7 天只测试一个主要变量

实验顺序：

1. 安装按钮文案和位置。
2. 一键安装与复制配置之间的选择。
3. 首个任务是否直接出现在安装完成页。
4. 默认推荐 `search_official_docs` 还是 `verify_web`。
5. 市场页面定位：工具发现，还是官方资料验证。

每次实验都要记录：

- 起止日期。
- 入口和来源。
- 唯一访问或安装数。
- 初始化数。
- 首次成功 Agent 数。
- 7 日重复 Agent 数。

终止规则：连续两个 7 日窗口没有带来合格 Agent，暂停该渠道；带来至少 5 个合格 Agent 且激活率高于总体基线的渠道，增加投入。

#### 步骤 4.4：达到 50 后确认价值场景

将真实使用按任务分为：

- 官方文档搜索。
- 网页理解与验证。
- 工具发现与比较。
- 工具/服务商检查。
- 已登记只读工具调用。

选择合格 Agent 数、重复使用率和成功率最好的前两个场景作为下一阶段主入口。不要依赖口头偏好决定定位。

#### 步骤 4.5：达到 100 后设置产品方向决策门

只有满足以下条件，才讨论下一层信用基础设施：

- 至少 100 个合格外部 Agent。
- 7 日重复使用率达到 20% 以上，或已经明确知道不重复的原因。
- 至少 3 个独立客户端来源。
- 至少 3 个工具/服务商产生持续真实调用。
- 数据可以区分成功、失败、版本和服务商，不依赖原始隐私内容。

未满足时，继续修复安装、激活和使用价值，不开发 Agent 信用平台。

### 阶段 5：建立可复利的工具可信数据

时间：与 10 → 100 增长并行，但不得阻塞获客。

#### 步骤 5.1：保存最小必要证据

每次调用只记录：

- 不可逆 Agent ID HMAC（如果存在）。
- 不可逆 Session HMAC（如果存在）。
- `request_id`。
- 来源和客户端类别。
- 工具、服务商和版本。
- 开始、结束时间与延迟。
- 成功/失败和标准错误代码。
- 结果数量，不保存结果内容。
- 外部、内部、探针或匿名分类。

不记录：

- 原始 Agent ID 或 Session ID。
- IP 地址。
- 提示词。
- 工具参数。
- 工具结果正文。
- API Key、Cookie 或其他凭据。

#### 步骤 5.2：形成工具和服务商历史

为每个工具和服务商计算可解释的运行证据：

- 最近验证时间。
- 7/30 日可用率。
- 成功调用数和独立 Agent 数。
- P50/P95 延迟。
- 错误类型分布。
- 已验证客户端兼容性。
- 版本变化前后的成功率。
- 证据样本量和新鲜度。

这不是“绝对信用分”。页面和 API 必须展示证据量、时间窗口和来源，避免把少量样本包装成权威结论。

#### 步骤 5.3：建立数据保留和完整性规则

- 原始事件采用追加写入，不在原记录上修改结果。
- 聚合结果可以重算。
- 内部和探针事件永久与外部指标分开。
- 定义事件保留周期和删除机制。
- 为 HMAC 密钥建立轮换方案，同时保留合理的去重连续性。
- 指标口径变更必须版本化并说明前后差异。

#### 步骤 5.4：提供内部增长与可靠性面板

面板必须回答：

1. 今天和本周新增多少合格 Agent？
2. 距离 1,000 还差多少？
3. 哪些来源带来真实成功？
4. 哪一步流失最多？
5. 哪个工具或服务商失败最多？
6. 哪个客户端出现协议兼容问题？
7. 7 日和 30 日重复使用如何？

先使用现有 Postgres 查询和轻量页面/API，不引入新的数据仓库。

### 阶段 6：从 100 扩展到 300、600、1,000

时间：2026-10-01 至 2026-12-31。

#### 步骤 6.1：只扩张已验证渠道

达到 100 后，把时间集中在最多三个渠道：

- 一个 MCP/Agent marketplace 渠道。
- 一个开发者客户端生态渠道。
- 一个工具作者或团队合作渠道。

每个渠道必须已经产生合格 Agent。没有成功调用的“大曝光”不扩张。

#### 步骤 6.2：建立工具作者增长回路

对已登记工具作者提供：

- 兼容性检查结果。
- 真实成功调用数和独立 Agent 数。
- 可用率、延迟和错误分类。
- 可嵌入的“Verified by 404.directory”证据链接，明确时间窗口和样本量。
- 一条让其用户通过 404.directory 调用工具的安装入口。

增长回路：

```text
工具作者接入
  → 404.directory 验证和调用
  → 产生真实兼容性与可靠性证据
  → 工具作者分享证据和安装入口
  → 新 Agent 使用
  → 更多跨客户端运行证据
```

这比单纯增加目录条目更可能形成网络效应。

#### 步骤 6.3：建立 Agent 客户端合作回路

向客户端或 Agent 框架提供：

- 标准 MCP 安装入口。
- 默认稳定身份但不暴露原始 ID。
- 工具发现和官方资料搜索场景。
- 兼容性报告。
- 按来源统计的匿名聚合结果。

合作目标不是宣布伙伴关系，而是让其真实用户完成调用。

#### 步骤 6.4：在 300 和 600 时分别复盘

每个里程碑检查：

- 是否仍由一个来源占绝大多数。
- 新 Agent 是否只是一次性试用。
- 成功率是否随规模下降。
- 匿名请求比例是否下降。
- 是否出现伪造身份、重复安装或异常流量。
- 哪些工具开始产生稳定跨客户端证据。

如果单一来源超过 70%，必须发展第二来源；如果 7 日重复使用低于 15%，暂停扩张并修复产品价值。

## 6. 里程碑和所需增长速度

从 2026-08-23 的 1 个 Agent 到年底 1,000 个，剩余约 130 天，需要平均新增约 7.7 个/天、54 个/周。

| 日期 | 累计目标 | 阶段判断 |
| --- | ---: | --- |
| 2026-08-31 | 10 | 发布闭环和首批外部试点完成 |
| 2026-09-15 | 50 | 至少一个渠道可以重复带来真实 Agent |
| 2026-09-30 | 100 | 首次产品方向决策门 |
| 2026-10-31 | 300 | 两个以上有效来源，可靠性数据开始有意义 |
| 2026-11-30 | 600 | 扩张有效渠道，同时控制重复与异常流量 |
| 2026-12-31 | 1,000 | 完成严格年度目标 |

这些是执行目标，不是预测或保证。任何里程碑未完成，都必须报告真实差距，不能用匿名调用、内部测试或页面流量补数。

调整规则：

- 落后一个周目标：修复最大漏斗问题并减少低价值工作。
- 连续两周落后：停止新增功能，重新分配全部时间到外部试点和有效渠道。
- 连续两个里程碑落后：重新评估目标、定位或分发方式，并明确需要的外部资源；不伪造进度。

## 7. 每周执行节奏

### 周一：数据和可靠性

- 固化上周结束时的严格指标快照。
- 查看来源、客户端、工具和服务商成功率。
- 选择本周唯一最大问题。

### 周二：修复最大阻塞

- 只修复安装、首次调用或主要可靠性问题。
- 为修复增加自动测试和生产验收条件。

### 周三：外部试点

- 帮真实外部用户完成安装和首个任务。
- 记录失败阶段，不收集提示词或结果内容。

### 周四：分发和合作

- 跟进一个高价值目录或客户端生态。
- 更新已发布版本、安装证据和真实用例。
- 不重复提交已经在审核队列中的仓库。

### 周五：实验结算

- 计算该渠道带来的合格 Agent、首次成功率和 7 日重复率。
- 决定继续、扩大、修改或停止。
- 发布内部周报。

### 周末：自动监控，不扩张范围

- 检查生产健康、服务商可用率和错误异常。
- 不因为偶发想法加入新功能。

## 8. 推荐架构调整

短期保持单一后端和 Postgres，不做微服务化。按逻辑边界整理即可：

```text
Agent 客户端
    |
    +-- Remote MCP /mcp
    |
    +-- npm stdio identity bridge
            |
            v
    MCP 协议与身份上下文层
            |
            v
    工具发现 / 验证 / 比较层
            |
            v
    只读 Gateway Provider 连接层
            |
            +-- OpenAI
            +-- Microsoft Learn
            +-- AWS
            +-- Cloudflare
            +-- Hugging Face
            +-- DeepWiki
            |
            v
    隐私安全调用事件层
            |
            v
        Postgres
            |
            +-- 严格 Agent 指标
            +-- 激活漏斗
            +-- 工具/服务商可靠性证据
```

### 8.1 立即调整

- 把“协议适配”“工具逻辑”“服务商连接”“遥测聚合”保持为清晰模块。
- 所有入口统一进入同一调用记录路径，避免 MCP、REST 和 Gateway 数据口径不同。
- Provider connector 使用统一超时、重试、错误代码和结果数量接口。
- 所有内部测试带稳定内部分类，不依赖名称猜测排除。
- 聚合指标从追加事件计算，指标定义版本化。

### 8.2 达到 100 Agent 后再评估

- 是否需要签名执行回执试点。
- 是否需要由工具服务商共同证明调用结果。
- 是否有外部系统愿意使用 404 的可靠性判断。
- 是否存在跨客户端稳定身份的真实需求。

### 8.3 现在不调整

- 不拆独立身份服务。
- 不拆独立信用或风险服务。
- 不建立保险引擎。
- 不建立区块链账本。
- 不建立复杂推荐模型。

这些能力只有在真实数据和依赖方出现后才有价值。

## 10. 风险和处理

| 风险 | 触发信号 | 处理 |
| --- | --- | --- |
| npm OIDC 配置失败 | tag 工作流无法发布 | 检查仓库、workflow 和 package ownership；用户在 npm 后台重配；不泄露凭据 |
| Registry 更新延迟 | npm 已发布但 latest 未变化 | 验证 `server.json`，等待合理同步窗口并跟进官方渠道 |
| 匿名流量很多 | 初始化上升但合格 Agent 不变 | 优先推动身份桥安装；匿名调用继续可用但不计目标 |
| 外部目录长期不审核 | PR/提交数上升但没有来源流量 | 停止重复跟进，转向可直接触达的开发者和工具作者 |
| 指标被自测污染 | 发布后 Agent 数异常增长 | 内部 ID、来源和分类三重排除；抽查异常序列 |
| 重复/伪造身份 | 单一来源短期出现大量一次性 ID | 频率与行为异常检测；不直接计入；人工复核 |
| 第三方 Provider 宕机 | 某工具失败率突然升高 | 熔断、清晰错误、状态展示；不要把 Provider 失败计成 Agent 失败 |
| 隐私风险 | 日志出现原始 ID、参数或结果 | 立即停止相关写入，清理和轮换密钥，补充测试与审计 |
| 过早平台化 | 开发任务与安装、调用、数据无关 | 按产品边界拒绝，放入 100 Agent 后决策清单 |

## 11. 从工具证据走向信用层的条件

长期方向可以是 Agent 信任、身份和风险基础设施，但不能靠概念直接搭建。正确顺序是：

```text
可安装工具
  → 真实 Agent 调用
  → 隐私安全运行证据
  → 工具/服务商可靠性历史
  → 多方可验证执行回执
  → 稳定 Agent 身份
  → 场景化信誉与风险判断
  → 在法律与真实交易数据成熟后评估保险
```

下一层不是“万能评分”，而是回答具体问题：

- 这个 Agent 是否曾经在多个独立工具上可靠完成过同类任务？
- 这个工具在当前客户端和版本下是否稳定？
- 这次操作应当允许、限制、要求额外验证，还是拒绝？

在没有独立外部 Agent、独立工具服务商和可验证结果之前，不能声称已经形成 Agent 信用。
